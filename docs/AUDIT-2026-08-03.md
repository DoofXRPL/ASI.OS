# ASI OS — audit and route to Beta

A point-in-time audit, taken at commit `0302cc4` on 2026-08-03, and the sequence
of work it recommends. It is dated because it is a reading of a moment, not a
living document: where it disagrees with the code, the code is right and this
file is old.

[docs/IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) remains the plan of record
for what the phases are. This file records what is actually built, what is wrong
with it, and the order in which to fix and extend it. Where the two conflict, §3
of this document says so explicitly rather than quietly winning.

Every claim here was checked against the code. Where a defect is asserted, the
file and the reason are named, and the ones that could be demonstrated were run
rather than reasoned about.

---

## 1. What exists

Phase 0 is complete and Phase 1 is roughly two thirds done. At this commit the
count is 137 RLS tests and 274 unit tests, all passing, with `npm run verify`
green in CI's own order.

### Surfaces

| Route | Renders | State |
| --- | --- | --- |
| `/` | The public product document | Working |
| `/early-access` | The request form, gated and metered | Working |
| `/login` | Password sign-in, or the names of the missing variables | Working |
| `/auth/callback` | Code exchange, redirect validated against an allow-list | Working |
| `/today` | A state derived from projects and captures | Working |
| `/inbox` | Capture, and four ways out | Working |
| `/projects`, `/projects/[id]` | Outcome, status, next action, required reason when blocked | Working |
| `/activity` | The append-only trail, paginated | Working |
| `/settings` | Display name, time zone, time format | Working, with the defect in §4.1 |

Decisions, Memory and Connections do not exist and return 404, which
[ADR 0002](DECISIONS/0002-navigation-earns-its-place.md) requires. Nothing in the
navigation leads anywhere empty.

### The spine that makes it trustworthy

These are the parts that are genuinely production-ready, in the sense that they
are enforced by the database or by a test rather than by care:

- **Isolation.** Five `public` tables, every one with `user_id uuid not null`,
  RLS enabled, and owner-scoped policies. `anon` holds no privilege on any of
  them. Column-level grants mean `profiles.is_owner` cannot be self-granted and
  `inbox_items.content` cannot be rewritten — capture is preserved by privilege,
  not by convention.
- **A schema that cannot grow silently.** `tests/rls/isolation.test.ts`
  enumerates the schemas and the tables in `public` and asserts the expected set.
  A new table without tests fails CI, and so does a new `public` function that
  does not pin `search_path`.
- **The front door.** `public.request_early_access()` is the only reachable path
  into `access`, requires a key the database verifies as a digest, and meters
  every caller with an atomic conditional upsert whose `WHERE` clause *is* the
  decision. No raw address reaches any table; the `bucket` CHECK constraint
  accepts nothing but a 32-character digest or the literal `deployment`.
- **Derivation with evidence.** Everything `/today` asserts comes from a pure
  function in `lib/derive/` and carries the id of a row it was given. There is no
  invented deadline, priority or score anywhere.
- **Honest reads, mostly.** Query helpers return `ReadResult<T>` and pages render
  `Failed`. The exceptions are named in §4.1.
- **A guard against the one mistake that would undo all of it.**
  `scripts/guard-service-role.ts` fails the build if `app/`, `lib/` or
  `components/` could reach the database as anything but the signed-in user.

### The layers that do not exist yet, by design

No AI layer, no integrations, no external network calls, no queue, no
`app/api/`. That is deliberate and should stay true until Phase 2 is chosen
deliberately rather than drifted into.

## 2. Architecture critique

The architecture is better than it needs to be for its size, and the criticisms
below are adjustments rather than rewrites. Nothing here recommends replacing a
working system.

**What is right, and worth not disturbing.** The dependency direction
(`components` → `app` → `lib` → Postgres) is respected with no cycles. Identity
resolves in exactly one place. Business logic that can be pure is pure and is
unit-tested without a database. RLS is treated as the boundary rather than as
defence in depth, and the test suite proves it against real policies and real
accounts rather than mocks. The decision to run the RLS gate against plain
PostgreSQL instead of the Supabase CLI keeps a required gate fast and Docker-free
and should be kept.

**Where it is weaker than it looks:**

1. **The write contract is honoured by four helpers out of five.**
   `WriteResult<T>` promises that a failure is reported. `updateSettings` does
   not check that a row was affected, so it reports success for a write that did
   nothing. Detail and consequence in §4.1. This is the single most important
   finding in this audit, because the failure is silent in both the UI and the
   audit trail.

2. **Two read helpers opt out of `ReadResult` without saying why.**
   `getSettings` discards the query error entirely and returns
   `DEFAULT_SETTINGS`; `getProfile` returns `null` for "no such row" and for "the
   database is unreachable" alike. Hard rule 11 exists because an empty account
   and a broken database must not look the same, and here they do. `getSettings`
   has a stated reason — a malformed settings row should not lock someone out —
   but that argument covers a malformed row, not an unreachable database, and the
   code cannot tell them apart.

3. **The OS `Field` builds the link between a control and its error, and only
   attaches one end of it.** `components/ui/field.tsx` derives an id, puts it on
   the error or hint paragraph, and never tells the control the id exists — no
   `aria-describedby`, no `aria-invalid`. On every private form a screen reader
   therefore announces the label and not the error. The public early-access form
   does this correctly through an explicit `describedBy()` helper, which makes
   the gap a divergence between two form systems rather than an oversight in
   one.

4. **The dark and light form systems are parallel implementations.**
   `components/ui/field.tsx` and `components/site/form/` have the same geometry
   and different palettes. The split is deliberate and documented, and it is
   still two places to fix a behaviour. Worth leaving alone until a third
   palette or a second such bug argues otherwise; worth not extending.

5. **`revalidatePath` is called with hardcoded path lists in four action files.**
   Correct today. It means a new surface that reads projects will silently serve
   stale data until somebody remembers to add it to `refresh()`. A tag would
   move that from memory to declaration, and Next 16 supports it.

6. **Small duplications that are cheap to leave and cheaper to name.** Two
   different first-line-of-a-capture truncations (80 characters in
   `lib/derive/attention.ts`, 120 in `lib/schemas/inbox.ts`); two `optionalText`
   Zod helpers with the same name and different empty-string semantics
   (`null` in one, `undefined` in the other); `"Supabase is not configured."`
   written out in five modules; three near-identical save-and-confirm form
   footers under `app/(os)/projects/[id]/`. None of these is a defect. The
   `optionalText` pair is the one that could become one, because the name implies
   the behaviours agree.

7. **CI has no permissions block and pins actions to floating tags.** A single
   `verify` job on `ubuntu-latest`, correct in content and order, using
   `actions/checkout@v4` and `actions/setup-node@v4` with default `GITHUB_TOKEN`
   permissions. For a private single-owner repository the exposure is small; the
   fix is three lines.

8. **No Content-Security-Policy.** `next.config.ts` sets
   `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options` and
   `Permissions-Policy`, and stops there. A CSP is the header that matters most
   for a surface that will eventually render model output, and it is much easier
   to add now, while there is no inline script to grandfather in, than after
   Phase 2.

**What should be removed:** nothing. No dead code, no unreferenced modules, no
commented-out blocks, and no `TODO`, `FIXME`, `HACK` or `XXX` anywhere in `app/`,
`lib/` or `components/`. That is unusual and worth preserving.

## 3. Technical debt, in priority order

Severity is about consequence, not effort. "Silent" means the system continues
and reports success.

| 2 | A failed settings or profile read is indistinguishable from an empty one | **High, silent** | `lib/db/settings.ts`, `lib/db/profile.ts` |
| 3 | Private forms never associate their errors with their controls | Medium | `components/ui/field.tsx` and its seven callers |

### On finding 1, because it is the one that matters

`updateSettings` issues an `UPDATE` with no `RETURNING` and treats the absence of
a PostgREST error as success:

```ts
const { error } = await supabase
  .from("user_settings")
  .update({ settings: merged as unknown as Json })
  .eq("user_id", userId);

if (error) return { ok: false, error: error.message };
return { ok: true, data: merged };
```

An `UPDATE` matching no rows is not an error. Run against the real schema, with
the caller's settings row absent and the statement executed as that caller under
RLS: `rowCount` is 0 and nothing is raised. Every other write helper in `lib/db/`
guards against exactly this with `.select("*").maybeSingle()` and a `!data`
check — `updateProject` answers `"No such project in your records."`

The consequence is not only a wrong return value. `saveSettingsAction` writes the
audit event *on the strength of that return value*:

```ts
const result = await updateSettings(session.user.id, { timeFormat });
if (!result.ok) return { error: result.error, saved: false };

await recordActivity(session.user.id, {
  eventType: "settings.updated",
  summary: `Time format changed to ${timeFormat}`,
  ...
});
```

So the trail records "Time format changed to 24h" for a change that did not
happen, and the form says "Saved." That is a direct violation of hard rule 10 —
audit writes must record what actually changed — reached through a violation of
the `WriteResult` contract. A history that can contain entries for changes that
never occurred is worse than no history, which is the reasoning that rule already
states.

Finding 2 makes it reachable rather than theoretical. `getSettings` discards its
read error, so a failed read returns `DEFAULT_SETTINGS`; the action then compares
the submitted time format against a default rather than against what is stored,
and can conclude "unchanged" and silently discard the change, or "changed" and
write an event about a value it never read.

### On finding 5, and how to resolve it without deleting history

`docs/IMPLEMENTATION_PLAN.md` is the plan of record and most of it holds. Four
regions describe things that were never built and read as though they were
current:

- §6 proposes `middleware.ts` (the file is `proxy.ts`), `lib/ai/`,
  `lib/coordinator/`, `lib/memory/`, `app/api/coordinator`, `AppShell`,
  `RuntimeStatus` and shadcn. None exist.
- §7 gives `inbox_items.kind` a `thought` value, splits `processed_into` into
  `processed_into_type`/`processed_into_id`, and gives `projects` a `priority`
  and a `target_date`. The migrations have none of these, and
  [ADR 0003](DECISIONS/0003-projects-hold-the-next-action.md) is the reason.
- §14 says RLS runs against a local Supabase stack via the CLI in CI. It runs
  against a PostgreSQL service container.
- §15 says the RLS tests prove isolation on "all three tables". There are five.

The fix is to mark these as targets rather than descriptions, not to delete them.
A plan is allowed to describe a future; it is not allowed to be unreadable as to
which parts are the future. Same for `lib/auth/getUser.ts` in §33, which is
`lib/auth/session.ts`.

### On finding 8, PR #3

`feat(inbox): capture in place` — 1,753 additions across 14 files, open since
2026-07-28, and now `CONFLICTING`. It is a genuine feature (the capture form in a
modal sheet over the current surface, with a keyboard shortcut) built to a
careful specification, and it is stale: it cites 189 unit and 69 RLS tests
against today's 279 and 137.

It also carries two decisions that need an owner rather than a merge. It adds
`@testing-library/react` and `happy-dom` as devDependencies and gives the unit
project a DOM, which changes what "unit tests, no I/O, always runnable" means. And
its own description reports the two `supabase/config.toml` defects that
[#8](https://github.com/DoofXRPL/ASI.OS/pull/8) has now fixed, having worked
around them outside the repository rather than touch a file its task did not
name — independent corroboration of that finding from a week earlier.

The recommendation is to decide the DOM-in-unit-tests question first, then rebase
it, rather than to rebase it and discover the question during review.

## 4. The route to Beta

Beta means: somebody other than the owner can be invited, sign in, use the loop
for real work, and trust what they are told. Not "the feature list is finished".
Read against that, the gap is smaller than the roadmap implies, and it is mostly
about honesty and onboarding rather than about surface area.

The milestones below are ordered so that each one is shippable on its own and
nothing later is blocked by a decision that has not been made yet.

### M1 — The verification story holds

**Purpose.** A contributor can start the stack, and the gate that guards the
isolation boundary runs the database the stack runs. Without this, every later
milestone is developed against something other than the deployment target.

**Dependencies.** None. **Complexity:** small. **Risk:** low — no application
code, no schema.

**Files.** `supabase/config.toml`, `tests/unit/supabase-config.test.ts`,
`.github/workflows/ci.yml`, `tests/rls/harness.ts`.

**Status.** Written and verified, open for review in
[#8](https://github.com/DoofXRPL/ASI.OS/pull/8).

### M2 — Nothing reports a success it did not have

**Purpose.** Close findings 1 and 2. This is first among the code work because
the audit trail is the product's memory, and an entry that describes a change
that did not happen is a corruption of it, not a cosmetic bug.

**Dependencies.** None. **Complexity:** small. **Risk:** low, and it lowers
risk — the change turns a silent wrong answer into a visible one.

**Files.** `lib/db/settings.ts`, `lib/db/profile.ts`,
`app/(os)/settings/page.tsx`, `app/(os)/settings/actions.ts`, plus RLS coverage in
`tests/rls/` for the zero-row case and a unit test for the read contract.

### M3 — Every form says what is wrong, to everybody

**Purpose.** Close finding 3. An invite-only product whose first screen is a form
cannot have forms that announce errors only visually.

**Dependencies.** None. **Complexity:** small. **Risk:** low; presentation only.

**Files.** `components/ui/field.tsx` and its callers — `app/login/sign-in-form.tsx`,
`app/(os)/settings/settings-form.tsx`, `app/(os)/inbox/process-form.tsx`,
`app/(os)/projects/new-project-form.tsx`, and the three under
`app/(os)/projects/[id]/`. Plus `components/os/account-panel.tsx` for the missing
pending state on sign-out.

### M4 — The documents agree with the code

**Purpose.** Close findings 5, 9, 10, 11 and 12. Cheap, and it is the difference
between documentation that is read and documentation that is checked against the
source every time because it might be lying.

**Dependencies.** None. **Complexity:** small. **Risk:** none; prose only.

**Files.** `docs/IMPLEMENTATION_PLAN.md`, `docs/DATA-MODEL.md`,
`docs/ARCHITECTURE.md`, `README.md`, `app/page.tsx`,
`scripts/guard-service-role.ts`, `lib/supabase/database.types.ts`.

### M5 — A new public surface cannot escape the language rule

**Purpose.** Close finding 6. `tests/unit/landing.test.ts` scans a hardcoded map
of modules, and says so in a comment: "a page that is not listed is a page the
rule does not reach." Reading `lib/site/` from the filesystem makes forgetting
impossible rather than merely discouraged, which is the pattern the RLS schema
enumeration already uses.

**Dependencies.** None. **Complexity:** small. **Risk:** low.

**Files.** `tests/unit/landing.test.ts`.

### M6 — The invitation works end to end

**Purpose.** Beta's first requirement. Today an account is created by hand and
the owner is the only account there has ever been. The invite path — issue,
accept, land signed in with a provisioned profile and settings row — has never
been exercised. `handle_new_user()` is tested at the database level; the journey
is not.

**Dependencies.** M1 (needs a local stack to exercise mail), M2 (an invited user
whose settings row is missing must not be told "Saved.").

**Complexity:** medium. **Risk:** medium — it touches authentication, which is
the one thing whose failure is unrecoverable for the person locked out.

**Files.** `app/auth/callback/route.ts`, `app/login/`, `lib/auth/`,
`supabase/config.toml` (mail), and a new RLS or integration test for the
provisioning journey.

### M7 — Onboarding is the first minute, not a checklist

**Purpose.** A new account currently lands on `/today` with the honest and
useless answer that there is nothing yet. The first minute should ask for the
time zone (which everything in `lib/format/datetime.ts` already depends on) and
take one capture, because a Today derived from one real row is the shortest true
demonstration of the loop.

**Dependencies.** M6, M2, M3. **Complexity:** medium. **Risk:** low.

**Files.** New route under `app/(os)/`, `lib/derive/` for the "is this account
new" predicate (pure, and tested without a database), `app/(os)/layout.tsx`.

**Constraint.** No fabricated sample data, no seeded example project. The
`NothingYet` state exists for this and there is deliberately no component for a
fake value.

### M8 — Export and delete

**Purpose.** The last of Phase 1, and the one a private intelligence layer cannot
launch a beta without. `app/(os)/settings/page.tsx` currently says so plainly:
"Self-service export and deletion are not built yet, so they are not offered
here." That sentence is honest and it is not shippable to a second person.

**Dependencies.** M2 (the write contract), M4. **Complexity:** medium.
**Risk:** medium — deletion is the one operation with no undo, and hard rule 5
means it must not appear before it works.

**Files.** `app/(os)/settings/`, `lib/db/`, new RLS tests proving a caller can
export only their own rows and that deletion cascades exactly as far as
`0001_foundation.sql` says.

### M9 — Headers worth having before there is model output to render

**Purpose.** Close finding 7. A CSP is much cheaper now than after Phase 2, and
Phase 2 is the phase that introduces content the owner did not write.

**Dependencies.** None, but best done before M10. **Complexity:** medium — the
cost is finding what the current pages actually need, not writing the header.
**Risk:** medium; a wrong CSP breaks the site in production and not in
development, so it needs a report-only step first.

**Files.** `next.config.ts`, `.github/workflows/ci.yml`.

### M10 — Phase 2, deliberately

**Purpose.** The reasoning layer. Out of scope for this audit beyond one
observation: [ADR 0001](DECISIONS/0001-single-coordinator.md) already decided one
Coordinator rather than a crew, and §17 of the implementation plan lists the
decisions still owed by the owner — model tier, AI SDK, whether shadcn enters the
component layer. Those are decisions, not tasks, and M10 should not start until
they are recorded as ADRs.

**Do not start M10 before M2 and M8.** Advisory output that a human approves is
only as trustworthy as the record of what was approved, and that record is the
audit trail M2 repairs.

### Order

M1 → M2 → M3 → M4 → M5 → M6 → M7 → M8 → M9 → M10, with M3, M4 and M5 available
to run in parallel with anything, since none of them touches the database or
authentication.

## 5. Implementation plan

One focused change per task. Each is independently revertible.

### T1 — Make the local stack start

Open as [#8](https://github.com/DoofXRPL/ASI.OS/pull/8). Recorded here for
sequence.

### T2 — `updateSettings` reports the write it actually made

**Objective.** `updateSettings` returns `{ ok: false }` when no row was updated.

**Reasoning.** It is the only write helper in `lib/db/` that does not verify a
row was affected, and the audit trail is written on the strength of its answer.
Finding 1.

**Files.** `lib/db/settings.ts`; a new case in `tests/rls/isolation.test.ts` (or a
sibling) for the zero-row update.

**Implementation.** Add `.select("settings").maybeSingle()` and a `!data` branch,
matching `updateProject`. The message should name the record, not the mechanism.

**Testing.** RLS test: delete the caller's `user_settings` row, attempt the
update as that caller, assert failure is reported. Positive control in the same
test proving the ordinary update still succeeds and returns the merged value —
without the control, a helper that always failed would pass.

**Rollback.** Revert one file. No schema change, no data migration.

### T3 — `getSettings` and `getProfile` return `ReadResult`

**Objective.** A failed read is distinguishable from an absent row.

**Reasoning.** Hard rule 11. Finding 2, and the reason finding 1 is reachable in
practice rather than in principle.

**Files.** `lib/db/settings.ts`, `lib/db/profile.ts`,
`app/(os)/settings/page.tsx`, `app/(os)/settings/actions.ts`, and any other
caller the compiler names.

**Implementation.** Return `ReadResult<T>`. Keep the existing tolerance for a
*malformed* settings row — that reasoning is sound and should survive as a
comment explaining why a parse failure still yields defaults while a query
failure does not. Pages render `Failed`. `saveSettingsAction` must refuse to
compute "changed" from a read it did not get.

**Testing.** Unit tests for the parse-versus-query distinction. The typechecker
finds the callers.

**Rollback.** Revert; the surfaces return to the previous behaviour, which is
wrong but not new.

### T4 — `Field` wires `aria-describedby` and `aria-invalid`

**Objective.** Every control rendered by `components/ui/field.tsx` is associated
with its error and hint.

**Reasoning.** The id is already computed and already on the message; only the
reference from the control is missing. Finding 3.

**Files.** `components/ui/field.tsx`, and its callers where the props are
currently passed by hand.

**Implementation.** Follow the pattern `components/site/form/field.tsx` already
uses — a `describedBy()` helper — rather than inventing a second one. Prefer
cloning props onto the child over asking every caller to remember.

**Testing.** This is the task that argues for a DOM in the unit project, which is
the open question PR #3 raises. Until that is decided, assert it in the pure
helper and check the rendered output by hand.

**Rollback.** Revert; presentation only.

### T5 — Sign-out shows that it is happening

**Objective.** The sign-out button in `components/os/account-panel.tsx` gets a
pending state.

**Reasoning.** It is the only submit in the private surfaces without one.

**Files.** `components/os/account-panel.tsx`.

**Testing.** Manual. **Rollback.** Revert one file.

### T6 — The documents stop describing things that were never built

**Objective.** Close findings 5, 9, 10, 11 and 12.

**Reasoning.** Finding 5 in detail above. Marking a target as a target costs
nothing and preserves the history; deleting it loses the reasoning.

**Files.** `docs/IMPLEMENTATION_PLAN.md` §6, §7, §14, §15 and the
`lib/auth/getUser.ts` reference; `docs/DATA-MODEL.md` table count;
`docs/ARCHITECTURE.md` layer tree (add `lib/early-access/`, `lib/site/`,
`lib/format/`, `components/site/`); `README.md` (`test:unit`, `test:all`,
`start`, and the `ASI_DEV_SIGN_IN_*` variables); `app/page.tsx` comment;
`scripts/guard-service-role.ts` reference to `lib/supabase/browser.ts`;
`lib/supabase/database.types.ts` to name the `failed` outcome.

**Testing.** `npm run verify`. Prose is not otherwise testable, which is the
argument for T7.

**Rollback.** Revert; no behaviour changes.

### T7 — The banned-language test reads the directory

**Objective.** A new module in `lib/site/` is scanned without being registered.

**Reasoning.** Finding 6. The test says in a comment that an unlisted page is
unreached; the RLS suite solves the same class of problem by enumerating from the
source of truth instead of a list.

**Files.** `tests/unit/landing.test.ts`.

**Implementation.** Read `lib/site/` from the filesystem and import each module,
excluding `motion.ts`, which is tokens rather than copy — and excluding it by a
named predicate with a reason, not by omission.

**Testing.** Add a module containing a banned phrase in a scratch file and
confirm the test fails, then remove it. A guard that has never failed is a guard
that has not been tested.

**Rollback.** Revert one file.

### T8 — CI least privilege and pinned actions

**Objective.** A `permissions:` block and SHA-pinned actions.

**Reasoning.** Finding 7. Three lines and two pins.

**Files.** `.github/workflows/ci.yml`.

**Testing.** The workflow run itself. **Rollback.** Revert.

### T9 — A Content-Security-Policy, report-only first

**Objective.** A CSP on every response.

**Reasoning.** Finding 7, and the timing argument: no inline script exists to
grandfather in yet, and Phase 2 will introduce content the owner did not write.

**Files.** `next.config.ts`.

**Implementation.** `Content-Security-Policy-Report-Only` first, both surfaces
exercised, then enforce. Next's own inline bootstrap needs a nonce; the light and
dark palettes and the `<noscript>` reveal fallback on `/` and `/early-access` are
the parts to check.

**Testing.** Load both public surfaces and every private one with the browser
console open under report-only, then enforce. This is the task in the list most
likely to break in production and not in development, which is why it is two
steps.

**Rollback.** Remove the header. Immediate and total.

### T10 — Decide the DOM question, then rebase PR #3

**Objective.** A recorded decision on whether the unit project may have a DOM,
and then either a rebased #3 or a closed one.

**Reasoning.** Finding 8. `npm run test` is documented as "unit tests only — no
I/O, always runnable". A DOM is not I/O, so the sentence survives, but it is a
change to what the fast suite is, it adds two devDependencies, and hard rule
about unnecessary dependencies applies. It should be an ADR either way, because
T4 wants the same capability and two tasks wanting it is the point at which the
answer should be written down rather than assumed.

**Files.** A new ADR in `docs/DECISIONS/`; then PR #3.

**Rollback.** Not applicable to a decision. If the answer is no, T4 is verified

deliberately absent here. [ADR 0003](DECISIONS/0003-projects-hold-the-next-action.md)
